# Device Ingestion & Communication Protocol Specification

This document defines the complete protocol contract between connected devices/edge nodes and the Operations Platform API.

---

## 1. Event Schema Specification

Events submitted by devices must adhere to the following schema (`schema_version: 1`).

### JSON Schema & Field Definitions

```typescript
interface DeviceEvent {
  event_id: string; // UUIDv4, globally unique identifier generated by the device
  device_id: string; // String identifier of the sending device (e.g. 'dev-001')
  seq: number; // Monotonically increasing integer per device (>= 1)
  ts: string; // ISO8601 UTC timestamp of device observation (e.g. '2026-10-24T12:00:00.000Z')
  type: string; // Event classification (e.g. 'telemetry', 'device.error', 'device.heartbeat')
  payload: Record<string, any>; // Arbitrary telemetry or status payload object
  schema_version: 1; // Integer schema version, strictly 1
}
```

### Constraints & Validation Rules

- **`event_id`**: Must be a valid UUIDv4 string.
- **`device_id`**: Must match the authenticated device bearer key. A device cannot submit events on behalf of another device.
- **`seq`**: Monotonic per device. Out-of-order delivery is tolerated; the server records events and updates `devices.last_seq = GREATEST(devices.last_seq, seq)`.
- **`ts` (Device Clock Skew Protection)**:
  - Timestamp must be valid ISO8601.
  - Server enforces a **future timestamp limit**: If `ts > NOW() + 5 minutes`, the event is rejected individually with `reason: "Timestamp cannot be more than 5 minutes in the future"`.
  - Server automatically appends `received_at: NOW()` upon PostgreSQL commit.
- **`payload`**: Must be a valid JSON object. Primitive types (strings, numbers, booleans) or nested objects are supported.
- **`schema_version`**: Must be integer `1`.

## 2. Ingestion Endpoint Specification

### `POST /v1/events`

Batch ingest endpoint for fleet devices. Supports batches from 1 up to **500 events per request**.

#### Headers

| Header             | Required | Value / Description                         |
| ------------------ | -------- | ------------------------------------------- |
| `Authorization`    | Yes      | `Bearer <raw_device_api_key>`               |
| `Content-Type`     | Yes      | `application/json`                          |
| `X-Correlation-ID` | Optional | Custom UUID for distributed request tracing |

#### Request Body

A JSON array of event objects (1 to 500 events):

```json
[
  {
    "event_id": "c1a2b3c4-d5e6-7890-abcd-ef1234567890",
    "device_id": "dev-001",
    "seq": 101,
    "ts": "2026-10-24T12:00:00.000Z",
    "type": "telemetry",
    "payload": {
      "temperature": 78.4,
      "humidity": 45.2,
      "battery": 92.5
    },
    "schema_version": 1
  }
]
```

#### Response (HTTP 200 OK)

The server returns HTTP 200 with an array containing the exact processing outcome for each submitted event in the batch:

```json
{
  "results": [
    {
      "event_id": "c1a2b3c4-d5e6-7890-abcd-ef1234567890",
      "status": "accepted"
    },
    {
      "event_id": "99999999-d5e6-7890-abcd-ef1234567890",
      "status": "duplicate",
      "reason": "Event already accepted for device"
    },
    {
      "event_id": "88888888-d5e6-7890-abcd-ef1234567890",
      "status": "rejected",
      "reason": "Timestamp cannot be more than 5 minutes in the future"
    }
  ]
}
```

## 3. Per-Event Status Semantics

| Status          | Meaning                                                                                                                                                       | Storage State                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **`accepted`**  | Event is structurally valid, authorized, within clock-skew limits, and **transactionally committed** to PostgreSQL.                                           | Inserted into `events` table with `processing_status = 'pending'`.   |
| **`duplicate`** | Event with the identical `(device_id, event_id)` was already committed in a prior request. Acknowledged safely without error.                                 | Existing row preserved; no duplicate row created.                    |
| **`rejected`**  | Event failed schema validation, has invalid timestamp skew (> 5 min future), or violates device ownership. Valid events in the same batch are still accepted. | Inserted into `rejected_events` ring-buffer audit table with reason. |

## 4. Backpressure & Rate Limiting Contract

### A. Queue Backpressure (`429 Too Many Requests`)

- When the pending queue depth in PostgreSQL exceeds `QUEUE_BACKPRESSURE_THRESHOLD` (default: 5,000), the API immediately sheds load.
- **HTTP Response Code**: `429 Too Many Requests`
- **Response Headers**: `Retry-After: 5`
- **Body**:
  ```json
  {
    "error": "Ingestion queue backpressure: pending depth (5214) exceeds threshold (5000). Retry after 5 seconds."
  }
  ```
- **Device Action**: Device must pause transmission, hold unsent events in its local buffer, and retry after the duration specified in `Retry-After`.

### B. Per-Device Rate Limiting (`429 Too Many Requests`)

- In-memory sliding window limiter tracks requests per device key.
- Default limit: **120 requests/minute per device**.
- **Response Headers**: `Retry-After: <seconds_until_window_reset>`
- **Body**:
  ```json
  {
    "error": "Rate limit exceeded for device dev-001. Retry after 24 seconds."
  }
  ```

## 5. Duplicate, Delay & Ordering Handling

### Idempotency Guarantee

The database enforces:

```sql
CONSTRAINT pk_events PRIMARY KEY (device_id, event_id)
```

Ingestion uses `ON CONFLICT (device_id, event_id) DO NOTHING`. Even if a network drop causes the device to resend an entire batch, zero duplicate events are accepted or queued.

### Out-of-Order Delivery

Due to cellular reconnects, edge retries, or simulator chunk shuffling:

- Events may arrive with `seq: [1, 2, 5, 4, 3]`.
- All valid events are committed and stored.
- Device state tracks the maximum monotonic sequence:
  ```sql
  UPDATE devices SET last_seq = GREATEST(last_seq, $1), last_seen_at = NOW() WHERE id = $2;
  ```
- Queue processing executes rule evaluations against event payload contents independently of ingest sequence.

### Device Reconnect & Buffer Replay

- When offline, devices buffer events into local persistent storage (e.g., file-backed disk ring buffer).
- On reconnection, the device replays its backlog in chunks.
- The simulator purposefully re-transmits already-acknowledged events to prove idempotent dedup, and shuffles chunk ordering to verify out-of-order ingestion tolerance.

## 6. Precise Delivery Guarantees

| Stage                          | Guarantee                                         | Enforcement Mechanism                                                                                                                                                                               |
| ------------------------------ | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Device -> Ingestion API**    | **At-least-once transport, exactly-once storage** | Unique constraint `PRIMARY KEY (device_id, event_id)` with `ON CONFLICT DO NOTHING`.                                                                                                                |
| **Ingestion -> Queue**         | **Zero lost accepted events**                     | Synchronous PostgreSQL commit before returning HTTP 200 `accepted`.                                                                                                                                 |
| **Queue -> Worker Execution**  | **At-least-once claim, exactly-once processing**  | Workers use `SELECT ... FOR UPDATE SKIP LOCKED` with leases. On rule match, incident upsert, history, outbox, and marking event `done` occur in **one single database transaction**.                |
| **Outbox -> Webhook Sink**     | **At-least-once transport, exactly-once at sink** | Workers retry with exponential backoff + jitter and circuit breaker; every webhook request includes header `Idempotency-Key: <outbox_id>`. Receiver acknowledges duplicate deliveries idempotently. |
| **ChangeLog -> SSE Dashboard** | **At-least-once streaming with gap recovery**     | Continuous SSE stream backed by PostgreSQL `LISTEN/NOTIFY`. Reconnects supply `Last-Event-ID: <seq>` to replay missed rows, falling back to `resync_required` on large gaps.                        |
