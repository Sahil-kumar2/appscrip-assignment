# Failure Modes & Resilience Verification Matrix

This matrix documents the platform's behavior under real-world infrastructure, network, concurrency, and client failure modes, the evidence proving correctness, and remaining operational limitations.

---

## Failure Modes Matrix

| Failure Mode                                                                                        | Expected Platform Behaviour                                                                                                                                                                                                                                                                                                                                  | Verification Evidence / Automated Test                                                                                                                                                             | Remaining Limitation & Trade-Off                                                                                                                                 |
| :-------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Duplicate Delivery**<br>_(Device resends previously acked event)_                                 | Server checks `ON CONFLICT (device_id, event_id)`. First request returns `status: "accepted"`; second returns `status: "duplicate"`. Exactly 1 event stored in database. Worker processes once.                                                                                                                                                              | `tests/failure-scenarios.test.ts`<br>_(Scenario 1: duplicate delivery)_<br>`Metric: aps_events_ingested_total{status="duplicate"}`                                                                 | Monotonic sequence check does not reject historical events; relies strictly on UUID idempotency key `(device_id, event_id)`.                                     |
| **Accepted-but-Processing-Fails**<br>_(Poison payload, transient DB error, or rule crash)_          | Event committed to `events`. Worker fails processing; transaction rolls back. Worker catches error, increments `attempts`, sets exponential backoff on `locked_until`, and stores `last_error`. After `MAX_EVENT_ATTEMPTS` (5), transitions to `processing_status = 'failed'` (dead-letter).                                                                 | `tests/failure-scenarios.test.ts`<br>_(Scenario 2: accepted-but-processing-fails)_<br>`Metric: aps_event_processing_failures_total`<br>`Endpoint: GET /api/dead-letters`                           | Dead-lettered events remain in `failed` status until an operator inspects and triggers `POST /api/dead-letters/requeue`.                                         |
| **Worker Crash Mid-Processing**<br>_(SIGKILL / OOM / host reboot mid-transaction)_                  | Worker dies with active lease (`locked_until = NOW() + 30s`). Row remains `processing_status = 'processing'`. Once lease expires (`locked_until < NOW()`), restarted worker or peer replica reclaims row via `FOR UPDATE SKIP LOCKED`.                                                                                                                       | `tests/failure-scenarios.test.ts`<br>_(Scenario 3: worker restart mid-processing)_<br>`scripts/demo.sh` _(Step 5: docker compose kill worker)_                                                     | Event re-processing latency is bounded by `EVENT_LEASE_SECONDS` (default: 30s). An event claimed right before a crash will wait up to 30s before reclaim.        |
| **Zombie Worker / Lease Expiration Race**<br>_(Worker pauses due to GC/network, peer reclaims row)_ | Worker enforces atomic commit fencing: `UPDATE events SET processing_status = 'done' ... WHERE event_id = $1 AND (locked_until IS NULL OR locked_until >= NOW())`. If lease expired while worker paused, query matches 0 rows, throwing an exception and rolling back all mutations atomically. Peer worker processes cleanly with zero duplicate incidents. | `tests/adversarial-hardening.test.ts`<br>_(Scenario 1: Zombie Worker Lease Fencing)_                                                                                                               | Work done by zombie worker during paused iteration is discarded; bounded by `EVENT_LEASE_SECONDS`.                                                               |
| **Absence Monitor Ingestion Race**<br>_(Device transmits heartbeat while absence check runs)_       | Inside transaction, `AbsenceMonitor` queries fresh `last_seen_at` directly from `devices` table and guards incident creation with `ON CONFLICT (dedup_key) WHERE status IN ('open', 'acknowledged') DO NOTHING RETURNING id`. If fresh activity is detected, monitor skips triggering, preventing false absence incidents.                                   | `tests/adversarial-hardening.test.ts`<br>_(Scenario 2: Absence Monitor Race Defense)_                                                                                                              | If device transmits milliseconds _after_ absence transaction commits, incident opens and is auto-resolved on the subsequent event cycle.                         |
| **Notification Service Outage**<br>_(Webhook receiver down or returning 503/timeout)_               | Incident creation succeeds transactionally. Outbox attempts delivery; catches 503; records exponential backoff with jitter. Consecutive failures trip `CircuitBreaker` to `OPEN`, persisting state to DB and halting requests. When sink recovers, probe succeeds and delivers with `Idempotency-Key`.                                                       | `tests/failure-scenarios.test.ts`<br>_(Scenario 4: notification service down then up)_<br>`apps/worker/src/__tests__/notification-pipeline-real-db.test.ts`<br>`Metric: aps_circuit_breaker_state` | Outbox notifications reaching `MAX_OUTBOX_ATTEMPTS` move to `dead` state and require manual operator retry (`POST /api/incidents/:id/notifications/retry`).      |
| **Device Offline then Burst Replay**<br>_(Device silent for hours, then replays buffered backlog)_  | `AbsenceMonitor` creates absence incident and marks status `stale`/`offline`. On reconnect, device burst-replays backlog. On first event, absence incident is **auto-resolved** (`status: 'auto_resolved'`). Matching telemetry events deduplicate to a single threshold incident, bumping `occurrence_count`.                                               | `tests/failure-scenarios.test.ts`<br>_(Scenario 5: device offline then burst replay)_<br>`apps/simulator/src/__tests__/scenarios.test.ts`<br>_(offline-reconnect scenario)_                        | If device stays offline indefinitely without transmitting, absence incident stays `open` until manual operator acknowledgment or resolution.                     |
| **Queue Backpressure**<br>_(Ingest rate outpaces worker capacity > 5,000 events)_                   | API queries cached pending count. If pending depth >= `QUEUE_BACKPRESSURE_THRESHOLD`, API immediately rejects incoming request with `429 Too Many Requests` + `Retry-After: 5`. Database memory and WAL are protected from uncontrolled growth.                                                                                                              | `tests/failure-scenarios.test.ts`<br>_(Scenario 6: ingestion exceeding capacity)_<br>`Metric: aps_requests_429_total{reason="queue_backpressure"}`                                                 | Ingesting devices must honor the `Retry-After` header and hold events in edge buffers; devices lacking buffers will lose data if they drop 429 payloads.         |
| **Device Rate Limit Burst**<br>_(Device malfunctioning or loop transmitting)_                       | Sliding-window limiter detects request count exceeding limit (default: 120 req/min). Returns `429 Too Many Requests` with calculated `Retry-After` seconds.                                                                                                                                                                                                  | `apps/api/src/__tests__/rate-limiter.test.ts`<br>`Metric: aps_requests_429_total{reason="rate_limit"}`                                                                                             | Rate limiter operates per API instance in memory; in multi-instance API deployments, requires sticky IP routing or Redis/token-bucket synchronization.           |
| **Malformed Event Payloads**<br>_(Missing event_id, invalid types, future ts > 5m)_                 | Per-event validation isolates bad records. Valid events in the batch are committed (`status: 'accepted'`). Bad events return `status: 'rejected'` and are audited in `rejected_events` table (capped ring buffer). Zero invalid incidents created.                                                                                                           | `tests/failure-scenarios.test.ts`<br>_(Scenario 7: malformed payloads)_<br>`Endpoint: GET /api/dead-letters`                                                                                       | Ring buffer for `rejected_events` is capped at 10,000 rows to prevent unbounded disk growth; oldest rejections are deleted.                                      |
| **Malformed API Parameters / UUIDs**<br>_(Non-UUID in route parameters like /api/incidents/:id)_    | Endpoints validate UUID syntax. Global error handler intercepts PostgreSQL error codes `22P02`, `22007`, `22008` and returns structured `400 Bad Request` instead of uncaught `500 Internal Server Error`.                                                                                                                                                   | `tests/adversarial-hardening.test.ts`<br>_(Scenario 4: Fastify UUID Parameter Validation)_                                                                                                         | Malformed client queries are rejected with 400; client must supply valid UUID format.                                                                            |
| **SSE Reconnect & Replay Gap**<br>_(Dashboard reconnects or registers during event burst)_          | Browser `EventSource` reconnects with `Last-Event-ID: <seq>`. `addSubscriber` immediately catches up all change_log records committed between connection handshake and live listener attachment before streaming live events. Zero missed rows.                                                                                                              | `tests/adversarial-hardening.test.ts`<br>_(Scenario 3: SSE Gap Protection)_<br>`tests/failure-scenarios.test.ts`<br>_(Scenario 8: SSE reconnect)_                                                  | Replay window is capped at 500 events. If client was disconnected across > 500 change log entries, server emits `event: resync_required` forcing a REST refetch. |
| **Multi-Worker Claim Races**<br>_(Multiple worker replicas polling the same queue)_                 | Workers execute `SELECT ... FOR UPDATE SKIP LOCKED LIMIT N`. Each row is locked exclusively for the claiming transaction; peer workers skip locked rows immediately with zero collisions or deadlocks.                                                                                                                                                       | `apps/worker/src/__tests__/worker-real-db.test.ts`<br>_(two workers racing on the same events)_                                                                                                    | Worker polling frequency (default: 500ms) introduces up to 500ms latency between event insertion and initial processing pick-up.                                 |
| **Unbounded change_log Table**<br>_(System running continuously for weeks with millions of events)_ | Automated trigger `trg_cap_change_log` runs on `change_log` every 500 inserts, pruning rows older than 50,000 sequence IDs. Disk usage is bounded while preserving a generous 100x replay safety window.                                                                                                                                                     | `migrations/002_cap_change_log.sql`<br>`tests/adversarial-hardening.test.ts`<br>_(Scenario 5: Unbounded change_log Capping)_                                                                       | Historical streaming replay older than 50,000 events must rely on REST API queries rather than SSE sequence replay.                                              |
| **UI Memory Growth in Minimized Tab**<br>_(Tab backgrounded while high-rate telemetry streams in)_  | `PlatformContext` detects `document.hidden` and falls back from paused `requestAnimationFrame` to `setTimeout`, and hard-caps `rafBufferRef` to 500 items. Normalized store caps `liveEvents` at 250 and `seenSeqs` at 2000.                                                                                                                                 | `apps/web/src/store/PlatformContext.tsx`<br>`apps/web/src/store/platformReducer.ts`                                                                                                                | Oldest live events scroll off the in-memory display buffer once 250 events are exceeded.                                                                         |
| **Database Network Blip**<br>_(PostgreSQL temporarily unreachable during ingest)_                   | Fastify API returns `503 Service Unavailable`. Health probe `/readyz` fails immediately. Devices retry with exponential backoff. Once DB recovers, `/readyz` returns 200 and ingestion resumes.                                                                                                                                                              | `apps/api/src/__tests__/api.test.ts`<br>_(readiness check verifies DB connectivity)_                                                                                                               | If PostgreSQL is down, ingestion cannot accept events; devices must buffer locally on disk until database connectivity is restored.                              |
